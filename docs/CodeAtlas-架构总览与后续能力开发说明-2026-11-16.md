## 3. 架构数据与分析原则

源码、配置、构建文件和部署文件均来自固定SourceSnapshot。Java解析继续使用当前分析器，新增工程识别器通过统一结果适配接入。

建议采用ArchitectureDocument作为分析结果，包含schemaVersion、projectId、snapshotId、generationId、analyzerVersion、nodes、edges、groups、diagnostics、coverage和truncated。节点身份由固定来源、节点类型及规范键稳定生成；人工命名与位置分别保存为覆盖层。

| 字段组 | 建议内容 |
|---|---|
| 节点 | id、kind、name、responsibility、technology、parentId、evidenceIds |
| 节点种类 | SYSTEM、APPLICATION、MODULE、COMPONENT、EXTERNAL_SERVICE、DATASTORE、UNKNOWN |
| 关系 | id、source、target、kind、status、reason、evidenceIds |
| 分组 | 应用、业务模块或技术层；允许切换视角，保留原归属 |
| 证据 | 项目／快照／代次／文件／可选符号／精确范围／文件哈希／提取规则 |
| 来源级别 | 原始源码事实、配置声明、规则候选、AI候选、用户确认分别记录 |

CONFIRMED／INFERRED／UNRESOLVED沿用项目定义。配置声明使用某数据库时，事实可表述为“配置声明使用”，实际运行连接另需运行时证据。关系聚合保留原始证据集合及计数。AI推断和用户覆盖保留来源，原始索引继续可查询。

配置解析只提取白名单结构，过滤密码、令牌、认证URL及其他敏感值。源码注释和生成内容按不可信数据处理。分析期间保持静态读取，项目脚本执行属于单独受控实践行为。

## 4. 批次A 架构总览分析

### A01 工程与组件识别

复用snapshot、analysis、graph、store服务。建议新增architecture包及ProjectStructureAnalyzer、ArchitectureProjection等职责清晰的组件，名称可按项目约定调整。

- [ ] 从pom.xml／Gradle声明识别工程模块和依赖，限制文件数量、大小和解析深度；XML禁用外部实体，Gradle采用静态受限识别。
- [ ] 从启动类、Controller／Service／Repository等符号识别技术角色，命名推断保存规则与不确定性。
- [ ] 读取选定的application配置、package.json、API调用配置、Docker Compose等，识别应用、外部服务和数据组件。
- [ ] 保留动态配置、条件启用、多环境和缺失依赖的未确定状态，避免跨环境拼接成一个真实部署。
- [ ] 业务模块先按明确工程／包结构分组，可由用户修正。AI可起草名称和职责，经原预览授权链路生成候选。

验收样本覆盖单模块、Maven多模块、非标准目录、多个数据源、环境占位符、混合前后端、缺少配置、条件组件及恶意配置。每个节点和关系均可定位固定证据。节点数量、无法识别范围和截断必须可见。

### A02 查询与覆盖层

建议只读接口为GET /api/snapshots/{snapshot}/architecture，参数generationId、perspective、focusId、depth、limit。响应返回实际固定代次、规则版本、节点／边、分页／截断和分析覆盖情况。depth与limit设置明确上限，禁止无界遍历。

人工修改职责、分组及确认结果采用独立追加记录，绑定原架构投影及revision，具有理由、来源、幂等和冲突处理。若新增持久化模型，在执行时核对最高迁移版本再新增SQL；旧快照和旧关系图保持可读。已有关系修正可复用其行为模式，架构覆盖不直接改写源码分析事实。

验收覆盖跨项目／快照／代次拒绝、历史投影恢复、重建期间固定旧版、覆盖冲突、取消及重试、分页数量和旧payload缺字段。

## 6. 批次C archify导出

本机archify包声明private、版本2.17.0-dev.1、Node>=18、MIT。该观察仅针对当前本机包，分发前重新固定可用来源、完整许可、版本和子依赖。新用户环境应具备项目提供的运行组件，导出流程避免依赖开发者个人技能目录。

### C01 隔离适配验证

以确定的ArchitectureDocument样本转换为archify architecture JSON。检查分组、节点身份、关系文字、长标签、自环、主题和证据状态。执行其schema／布局验证与最终deliver，保存真实退出码及产物。比较受控CLI和可复用渲染模块两条部署方式，按许可、体积、维护和安全结果确定产品适配。

### C02 导出任务及工件

建议POST /api/architecture/exports创建任务，输入snapshotId、generationId、projectionId／digest、format、scope、theme和idempotencyKey。任务状态及错误沿用项目既有模式，返回工件身份与下载入口。缓存键包含投影摘要、渲染器版本及输出选项。

以独立临时目录和固定参数调用渲染器，设置时间、进程输出、文件大小及清理边界。禁止将标签或路径拼接进shell字符串。工件校验通过后原子发布，失败保留旧工件且不误返成功。

首批HTML及一种已验证的图片格式可独立交付，其他格式按能力矩阵逐项启用。导出附版本、证据状态和范围说明。HTML中的源码链接区分离线证据摘要与回到本机应用的链接；访问源码继续经过本机会话授权。独立文件剔除令牌、私有绝对目录及敏感配置，私有源码是否嵌入由用户显式选择范围。

验收覆盖离线打开、资源完整、转义／脚本注入、字体与中文、长标签裁切、导出取消、超时、并发幂等、下载权限、历史版本及工件清理。渲染器错误应给出可诊断信息。运行导出不默认向外部模型发送数据。

## 7. 流程图与时序图

### D01 流程图

先支持选定方法的控制流，提取顺序、条件、循环、返回及异常路径；业务跨方法流程采用单独视图，明确展开深度和未解析分支。业务解释可由AI生成候选，但每个步骤与源码证据关联，允许用户修正并保留来源。

流程节点、边及分支条件拥有稳定身份；空方法、嵌套控制流、递归、try/finally及异步入口均有预期样本。浏览和导出共用结构化模型，当前仅有文本业务流程说明的能力继续保留。

### D02 时序图

以选定入口和有界调用路径生成参与者、消息和顺序。静态源码顺序不自动代表完整运行时顺序。分支／循环／异步与未知接口目标显式表示，递归设置展开上限。远程调用与跨进程连接仅按可核对证据呈现。

先交付确定的局部时序，再扩展运行时证据接入。验收覆盖多实现、缺依赖、循环、异常、异步、重载及历史版本，节点消息均能定位调用点。需要运行时采样时单独定义授权和采集边界。

## 10. 私有GitHub认证与自动同步

公开导入保持现有流程。私有认证先确定支持范围和凭据方式，比较用户本机受限凭据与OAuth／GitHub App，按部署边界形成ADR。

凭据按最小仓库权限保管，支持撤销、轮换和过期反馈；任务和日志中剔除认证URL、token和原始错误敏感值。继续限制GitHub主机、协议、重定向、克隆超时、容量和暂存目录，检查Git配置／代理／过滤器继承。

同步先提供用户手动检查新版本，再选择是否定时。每次发现变更创建新快照／代次，旧知识及训练来源继续指向原版本。支持固定ref／commit、无变化去重、网络重试、活动任务互斥及用户取消。重命名、删除、权限撤销、强制推送及分支切换都有明确结果。submodule与LFS继续按独立支持清单实现。

## 11. 自动隔离执行

PR-05仍为独立安全准入。先选择受控训练类型与依赖版本，再设计独立Worker、临时工作区、受限用户、CPU／内存／时间／进程／磁盘、网络、依赖下载、凭据及宿主机隔离。执行器具有单独威胁模型和审计。

最小试点从预配置Java测试任务开始。构建脚本、插件和下载依赖均属于执行范围。容器控制接口及宿主机凭据保持隔离，执行结束清理，提交与报告绑定精确内容。结果区分PASSED／FAILED／ERROR／TIMEOUT，重试幂等，日志按限额保存和脱敏。安全准入通过前继续使用现有USER_REPORTED外部报告。
